## 한 줄 발명 요약

한글 공공문서를 조문·항·별표·서식 단위의 의미 구조로 해석한 뒤,
사람이 검토 가능한 HTML과 AI 처리 가능한 구조 표현을 동시에 생성하는
기술.

## 제품 포지셔닝

이 프로젝트는 "한글 문서를 텍스트로 바꾸는 도구"가 아니라,
**한글 문서를 웹에서 다시 살아있는 문서로 만드는 엔진**입니다.
그리고 그 살아있는 문서는 사람이 읽기 좋고, 동시에 AI가 다루기
좋은 쪽으로 가고 있다는 점이 차별점입니다. 냉정하게 말하면,
"예쁘게 렌더됐다" 수준이 아니라 **한글 문서 의미복원 → 활용
가능한 재표현** 단계까지 온 상태입니다.

## 차별 포인트 정리

### 1. 복잡한 한글 공문서의 의미 단위 보존

단순 텍스트 추출이 아니라 조문, 항목, 표, 별표, 서식 등 문서의
의미 단위를 분리·구조화하여, 국가과제 공고·계획서·지침류 문서의
논리 구조를 유지한 채 기계가 해석 가능한 형태로 변환합니다.

### 2. 질의응답형 탐색에 유리한 구조 표현

"누가", "무엇을", "언제까지", "어떤 조건에서"와 같은 실무형 질문에
대해, 전체 문서를 다시 읽지 않고도 관련 블록을 직접 찾을 수 있는
구조를 제공합니다. 일반 OCR 텍스트나 평문 Markdown보다 검색·질의
응답 정확도가 높아집니다.

### 3. 표·라벨·값 관계의 명시적 표현

국가과제 문서에서 자주 등장하는 라벨-값, 항목-세부내용,
구분-기준-비고 형태의 표 구조를 단순 시각 배치가 아니라 **의미
관계**로 표현합니다. 병합 셀 좌표 + 각 셀의 역할(label / value /
header / spacer) + 편집 가능 여부(editable) + 도메인 힌트
(institution_info / budget / schedule / performance_metrics /
personnel 등)를 같이 담아 LLM 및 규칙 기반 엔진이 값을 안정적으로
추출·비교·검증할 수 있습니다.

### 4. 한글 문서의 시맨틱 기반 HTML 렌더링

구조화된 중간 표현을 기반으로 사람이 읽기 쉬운 HTML 미리보기를
생성하면서도, 원문 의미 구조를 최대한 유지합니다. "기계가 읽기
좋은 표현"과 "사람이 검토하기 좋은 표현"을 **같은 IR에서 동시에**
만들어낸다는 점이 핵심입니다.

### 5. RAG 및 에이전트 워크플로우에 적합한 포맷

문서를 의미 단위별 청크로 나누고 각 블록에 안정적인 식별자
(`sec-0`, `par-s0-p3`, `tbl-s0-p4-c0`, `cell-s0-p4-c0-r1c2-p0` 등
위치 기반 영속 ID)와 역할 정보를 부여할 수 있어, 한글 문서 전용
검색, 근거 인용, 조건 검토, 체크리스트 생성, 자동 요약, 초안 작성
등 후속 AI 작업에 직접 활용하기 용이합니다.

### 6. 규정·공고·계획서와 같은 실무 문서 처리에 특화

일반적인 HWP/HWPX 변환기는 텍스트 덤프나 시각 복제에 치우치는
경우가 많으나, 본 방식은 국가과제 계획서, 공고문, 제출서식처럼
구조가 복잡하고 실무 질의가 빈번한 문서를 대상으로 실제 업무
활용성이 높은 구조화 결과를 제공합니다.

### 7. 원문 보존성과 후처리 확장성의 양립

원문 레이아웃·계층·표현 요소를 최대한 유지하면서도, 필요 시 LLM
친화 포맷, HTML, 검색 인덱스, 체크리스트, 폼 입력용 데이터 구조
등으로 재가공할 수 있어, 단순 변환기를 넘어 **문서 이해 및 자동화
플랫폼의 기반 기술**로 확장 가능합니다.

## 외부 평가 요약

### 평가 1 — 출력물 품질 (HTML 렌더링)

*(공고문/계획서류 실 HWPX 렌더 기준)*

| 항목 | 평가 |
|---|---|
| 문서 독해 흐름 유지 | 표·중첩표·병합셀이 섞여도 제목→본문→표→주석 흐름이 깨지지 않음 |
| 시맨틱과 시각의 균형 | 제목은 제목처럼, 표는 표처럼, 강조는 강조처럼 렌더됨 |
| 표 처리력 | 중첩표 평탄화 안 함, 좌우 비교표 구조 유지, rowspan/colspan 붕괴 없음 |
| 스타일 보존 | 폰트 크기로 제목 위계 / bold로 핵심 강조 / 색상 힌트 유지. 단 inline style 다수 → **class 승격 완료 (2026-04-24)** |
| LLM 질의응답 유리성 | stable id + label-value + 섹션 앵커링으로 QA 정확도 상승 |

### 평가 1 — 한계

1. **1:1 페이지 fidelity 아님** — 페이지 좌표/줄바꿈/박스 positioning은 PDF 렌더러와 다름. 단 편집/검색/QA/부분 수정 용도엔 semantic DOM이 오히려 우위.
2. **체계도/다이어그램** — 본문과 표는 잘 처리되지만 화살표 기반 다이어그램은 HTML table 흉내에 의존. 전용 semantic block / mermaid / positioned canvas fallback 필요.
3. **span-heavy output** — **class 승격으로 해결됨 (2026-04-24)**. 과거에는 DOM 반복이 많았음.

### 평가 2 — 제품적 설득력

이 엔진은 "한글 문서를 그냥 텍스트로 바꾸는 도구"가 아니라 한글
문서를 웹에서 다시 살아있는 문서로 만드는 엔진처럼 보인다. 그리고
그 살아있는 문서가 사람이 읽기 좋고, 동시에 AI가 다루기 좋은 쪽으로
가고 있다는 점이 크다.

한글 문서는 많은 도구가 결국 둘 중 하나다:
원문처럼 보이게만 하거나, 텍스트만 대충 뽑거나. 이 결과는 지금
**"질문 가능한 구조화 문서" + "사람이 볼 수 있는 문서형 HTML"**
사이에 꽤 좋은 균형점을 찾고 있다. 이건 진짜 차별점이 된다.

**특히 국가과제 공고, 계획서, 행정문서, 공문, 평가표 같은 표 중심
문서 도메인에 매우 강한 방향.**

## 청구 가능성 후보 (변리사 논의용)

이 목록은 변리사와 함께 청구 범위 / 선행 기술 대조를 거쳐야 합니다.

1. **표의 의미 역할 분류 파이프라인**
   - 입력: 셀 좌표 + 배경색 + 테두리 + 폰트 속성
   - 출력: 셀 역할 (header / label / value / spacer) + editable 플래그 + 도메인 힌트
   - 핵심: 배경색/폰트 굵기 기반 fingerprint → 테이블 전체 컨텍스트에서 상대적 분류

2. **LLM-writable 중간 표현**
   - 위치 기반 영속 ID 체계 (`sec-s{i}-p{j}-c{k}-r{r}c{c}`)
   - 재귀 중첩 표 ID 연속성
   - 편집 후 원 문서 재삽입을 보장하는 슬롯 모델

3. **도메인 힌트 자동 추론**
   - 표 구조 + 주변 문단 제목 + 셀 내용 패턴 매칭
   - 도메인 종류: institution_info / budget / schedule / performance_metrics / personnel 등

4. **컨테이너 무관 IR 구조**
   - HWP (OLE) 와 HWPX (ZIP+XML) 를 동일한 `IrDocument` 로 수렴
   - 둘 다 같은 MD/HTML exporter 통과 → 출력 품질 일관

5. **Verbatim 캐시 + 타입드 결합 writer**
   - 수정 없으면 byte-equal 라운드트립
   - 수정된 레코드만 재인코딩 (DEFLATE 호환성 이슈 회피 전략 포함)

## Prior Art 조사 리스트

- **neolord0/hwplib** (Java): Apache 2.0, reader+writer. 포지셔닝 유사하지만 시맨틱 layer 없음.
- **hahnlee/hwp-rs** (Rust): 읽기 전용. 시맨틱 없음.
- **edwardkim/rhwp** (Rust, WASM): `@rhwp/core` + `@rhwp/editor`. 편집기/렌더러. **의미 구조 추출 없음** — 시각 렌더링 중심.
- **golbin/hop**: rhwp 기반 Tauri 데스크탑 앱. 뷰어+에디터.
- **범용 markdown 변환기** (pandoc / markitdown 등): HWP 비대응 또는 텍스트 덤프 수준.

우리 차별점: **의미 기반 구조화 + 양방향 재표현 (HTML / 구조화 MD) 동시 생성**
— 위 선행 작업 중 어느 쪽도 동시에 제공하지 않음.
